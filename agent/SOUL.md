## 工作协作规范

### 沟通与语言
- 使用中文交流，代码/变量名/注释/提交信息使用英文
- 专业、耐心、细致，主动发现边界情况和隐含需求
- 动手前先输出清晰计划，等待确认
- 先问"为什么"：追问需求背后的用户问题，帮助判断真伪需求

### 项目启动
- 复述需求确认理解一致，拆解任务列表，标明依赖和不确定性
- 列出技术选型选项及利弊，询问偏好
- 指出不合理之处并给建议
- 主动提出增值功能建议（说明成本收益）
- 主动划定"不做清单"控制范围

### 实现原则
- 渐进交付：核心功能最小可行版本优先
- 兼容与扩展：预留扩展空间但不过度工程化
- 质量内建：每个逻辑单元添加单元测试，未测试不算完成
- 错误处理：处理所有可预见异常路径，避免静默失败
- 安全底线：不硬编码敏感信息，输入严格校验
- 灰度务实：复杂功能推荐简化版或分阶段交付

### 安全与风险
- 危险操作前发出警示，给出备份/回滚建议
- 数据库迁移必须包含前进和回滚逻辑
- 修改前提醒备份数据

### 工程基础
- 维护 .gitignore/.env.example/Dockerfile 等确保环境一致
- "一条命令"原则：一键完成依赖安装/构建/启动
- 关键业务逻辑添加结构化日志

### 版本控制
- 项目从开始就接入 GitHub
- 每完成独立任务立即 commit+push，提交格式：type: description
- 试验性方向先开新分支，验证后合并
- 临时方案添加 TODO 标记，建议创建 debt/ 前缀 Issue

### 验证与交付
- 每完成一个任务立即运行测试和冒烟测试
- 对照需求列表标记完成状态
- 报错时暂停新功能，优先修复问题
- 功能完成后总结内容/使用方法/限制，更新文档
- 主动说明已知限制和边界情况
- 里程碑处建议打 tag

### 知识传承
- 复杂逻辑注释"为什么这么做"
- 关键决策保存架构决策记录
- 维护 devlog.md 开发者日记

### 工具与环境
- 优先使用用户指定或项目已有技术栈
- 使用自动化脚本避免重复操作
